*The serving half of the Open Kernel Challenge: how I made SGLang serve an 816B model faster on a full 8×H200 node, with agents doing the work and one scored run a day.*

> **Disclaimer:** An early draft of this post was generated by Claude from my project notes and records. I edited it from there.

In [the first post](/2026/11/20/i-entered-a-gpu-kernel-contest-and-didnt-write-a-kernel/) I described entering a GPU kernel contest without writing a kernel. A small organization of AI agents did the work, and I made the decisions. That was the kernel track. This post is about the second track, which opened on Nov 12 and closed at the end of Nov 19, Pacific time.

The kernel track timed one layer of the model on one GPU, and I could score ten times a day. The serving track timed the whole model, all 816 billion parameters, served by SGLang on a full node of eight H200 GPUs to simulated users having long coding conversations. I got **one scored run a day**. Apart from three free one-load checks a day, which often waited many hours in the queue, my feedback came from boxes I rented by the hour.

I finished at **2.315×** stock SGLang, after seven judged runs and about **$685** of cloud spend, nearly all of it GPU time. As of Nov 24 the serving board is still private, so every other score I know of is self-reported. I'll update this post when the board opens, or write a follow-up if there's more to say. The most detailed public write-up so far, [Nate Mauer's](https://n8mauer.github.io/musespark-serving/), reports 2.386×, and in the contest Slack a few people mentioned scores of 3.0–3.8×, which I can only treat as anecdotes. If those numbers hold, I didn't win. This post covers what I had the agents build to get more feedback, where my own measurements misled me, and what one person with a day job can do in eight days.

## The serving track, briefly

I submitted a patch to SGLang (v0.5.23, under 400 KB, files under `python/sglang/` only) and a list of launch flags from an allowed set. The judge serves [Muse Spark Open](https://openkernelchallenge.dev) on one 8×H200 node with the contest's settings and plays multi-turn coding conversations at it.

- The workload is 13-turn conversations with a 74,160-token first turn, about 750 new tokens per later turn, and an average of 220 output tokens per turn, at 1, 4, 16 and 32 concurrent users.
- The contest's settings are tensor parallelism across the eight GPUs for attention, experts spread across the GPUs, FP8 KV cache, a hierarchical cache that spills to host memory, and 16K-token prefill chunks. Speculative decoding uses a small drafter (DFlash) that guesses 8 tokens ahead, and about 4 of the 8 are accepted per step.
- The score is the geometric mean of four ratios, one per load, so each load counts equally. A load's ratio is my throughput per GPU, read at stock SGLang's per-user speed, divided by stock's.
- The gates are later-turn time to first token within 2× stock's, GPU memory within stock + 2 GB, and answers that agree with stock's, checked by how far my next-token probabilities drift from stock's (KL divergence on the logits) and by rescoring my turns with stock.

Each day allowed one scored run and three free checks; a check runs one load and doesn't count. Runs went in priority order: the kernel track's top 50, then each kernel board's top 10, then the rest of the top 100. I finished that track at #302, so any job of theirs in the queue went ahead of mine.

A few terms come up a lot below. **Prefill** is processing the prompt before the first output token. A 74K-token first turn takes seconds, and the user waits for all of it; that wait is the **time to first token (TTFT)**. **Decode** is generating output, and with speculative decoding each step checks the drafter's 8 guesses in one pass of the big model. The **KV cache** is the per-token memory each conversation keeps so later turns don't recompute the prompt. When it runs out, SGLang moves some of it to host memory and has to load it back. Most of the model's layers use **sliding-window attention (SWA)**, which only looks back 2,048 tokens and so needs little cache; the rest attend to the whole conversation.

Runs and patches have short names. Patches are p1 to p25, numbered in the order I built them. Six of them reached a scored run (p13, p15, p16, p19, p21 and p24); the rest were folded into a later patch, replaced, or dropped. A suffix marks a variant of the same patch, so p21eq and p19nvls are p21 and p19 with one setting changed. My own 8×H200 batches are n14 to n21, and n20b was a second attempt at n20. fix1 is the validation run that tested the hang fix on real weights. The kernel-track names in the first post (v20, c16b, a22) are a separate series.

## Planning in October

I started planning this track on Oct 25, two days into the kernel track and almost three weeks before serving opened. The first plan was CPU-only and spent nothing on GPUs. The agents read the live rules page and saved a copy, pinned the SGLang source the judge would run, and estimated every lever from the kernel track's judge profiles of a single layer. Every number in that plan was marked as verified in the source, read from the judge's files, or estimated.

On Nov 1 I had them rewrite it. Three deep-research reports came in (from ChatGPT, Claude and Gemini), and the agents checked each one against the pinned source; ChatGPT's and Claude's held up and Gemini's didn't. With those, a determinism audit and that day's rules, plan v2 set five constraints for every port. Each weight could have only one copy in memory, the patch had to fit the size limit, everything had to be safe inside CUDA graphs, kernels had to compile at server start, and only the decode-side verify path would change at first, with prefill left at stock until I could time it against the latency gate. Then it set a build order, and one-GPU tests of the first pieces started on Modal the next day.

Planning early did help. When the track opened, the rules had been read three times, the one-GPU mini engine already ran the judge's image, and the constraint list caught most bad ideas before they cost anything. The track itself moved, though. It opened on Nov 12 instead of Nov 5, the patch limit dropped from 720 KB to 400 KB, and launch flags from an allowed set became legal, where the October plan had assumed I could only change code defaults.

![Figure 1. The Nov 1 build order against what happened, and the steps it didn't have](/assets/images/okc/serving-plan.svg)

The plan's ranking was wrong. It was built from what I could already measure, the kernel track's single-layer decode profiles, so it put decode first and prefill last. On the judge, prefill decided most of the score, and the biggest step (p21) wasn't on the plan at all.

## One layer, eight GPUs

Most of what happened next depends on how the model is split across the eight GPUs, so here is one layer before the runs. Each GPU holds an eighth of the attention heads and 32 of the 256 experts in every layer, and every GPU sees every token. Some work divides cleanly eight ways. Some is repeated on all eight GPUs. Some depends on which experts the tokens pick, and then the busiest GPU sets the pace for the other seven.

## Getting eight GPUs at all

For the kernel track, one H200 at a time on [Modal](https://modal.com) was enough. Serving needs eight in one box, a 533 GB gated checkpoint on that box, and the judge's container image. The agents spent the first two days on that.

The delay in getting the weights was mine. The October research had already flagged that the checkpoint is gated, with manual approval, but I didn't get around to requesting access until Nov 13, the day after the track opened, when boxes had already failed on it. While that was pending, the agents found the same checkpoint on AWS SageMaker JumpStart, and I accepted its license there. Then they learned that the bytes can only be read from inside SageMaker jobs, so they copied it out with a training job whose only work was writing files to my bucket. My Hugging Face access came through pretty quickly, within about an hour and a half, and I never used the copy.

There was no 8×H200 on demand either. A Modal request for one sat in a queue for 45 minutes without a container, so I moved to AWS Spot, first p5e in London at about $29 an hour and later p5en in Tokyo. Spot quota existed in only two regions, and a request for London was granted the same day.

Then came boxes that booted and couldn't do anything. Docker's storage on the Deep Learning AMI ignored its configured data root. Two boxes started, set up their disks, and only then found that the token had no access to the weights, which cost about $4.40 for nothing. Every boot script now checks access in its first seconds and uploads its logs even when it stops early.

At $30–42 an hour, idle time is the cost, so I had the agents write a small Rust job runner. Each box pulls jobs from an S3 queue, uploads results, and terminates itself when the queue is empty. On the busiest night two boxes spent 87–94% of their lives running jobs, and pulling the 543 GB of weights (the checkpoint plus the drafter) straight from Hugging Face took 92 seconds.

One monitor failed in a way that looked like an answer. For nine hours my Spot-capacity report said "no capacity anywhere". The cause was an expired AWS login, which the scanner read as an empty market. It now fails loudly.

## Run by run

### p13: kernels from the kernel track, and a hang that first showed up on eight GPUs

The first full patch, p12, ported my kernel-track work into SGLang: a fused verify attention and the NVFP4 expert kernel. My one-GPU tests passed. On eight, the server hung during startup while capturing CUDA graphs.

My one-GPU tests never sent a chunk with no tokens for a GPU's experts, so the bug first showed up at eight GPUs, and the usual tools didn't find it. Host stack traces showed every process waiting, which is what any hang looks like. What settled it was the GPU's own lightweight core dump, triggered on demand and read offline in cuda-gdb. It showed one block of my MoE kernel spinning at a barrier. A chunk of tokens had picked no experts on that GPU (the empty case in Figure 2), and the kernel read stale shared memory. The fix was two lines, a one-GPU test written for it hung on the old patch and passed 48/48 with the fix, and my own validation run then read 1.33× stock. That fixed patch became p13.

The judge read **1.070×**. At 16 users the later-turn latency broke the 2× gate, so that load scored 0.999, about stock's level.

### p15: 13 GB I hadn't looked for

The judge's report showed my weights using 82.96 GB per GPU against stock's 69.85. The total-memory gate passed because SGLang sizes the KV cache from whatever memory is free, so my extra 13 GB had come straight out of the cache and cut it from 1.89M to 1.12M tokens. My own validation logs showed the same 13 GB. Nobody had looked.

The cause took one GPU and about $0.60 to find. Each layer's repacked expert weights were carved out of a larger temporary buffer that had just been freed, and the rest of that block stayed pinned. Allocating the weights before any temporary existed left zero stranded, with byte-identical weights. **1.104×**, all four loads inside the gates.

### p16: grouped expert GEMMs for prefill

At the judge's 16K prefill chunk, my expert kernel was slower than stock's. For big chunks, p16 decodes four experts at a time into reused scratch memory and runs grouped matrix multiplies (GEMMs), keeping only the packed 4-bit weights resident. **1.218×.**

### p19: someone else had just written the better kernel

The agents went looking upstream for anything on Hopper NVFP4 MoE and found [sglang#50800](https://github.com/sgl-project/sglang/pull/50800). It was an open pull request with a grouped NVFP4 expert op for Hopper, opened that same day. The research agent first called it unusable for this model. The coordinating session read the code instead and found a per-route mode that let stock's own fused post-expert step finish the job.

Before porting it, I had the agents read the contest rules and terms for anything on third-party code. They found nothing against it, and I approved the port with its notices and credit kept. On one H200 at the model's shapes it ran 2.4–3.3× my own expert kernel at prefill sizes, and it replaced 137 KB of my code. **1.457×.**

### p21: the biggest step was making existing code run on my hardware

SGLang already had a sequence-parallel prefill path for this model, behind a launch flag. Without it, every GPU runs the pooler and unpooler (and the norms around them) for every token of the chunk, eight copies of the same work. With it, each GPU takes an eighth of the tokens for those parts. That's the p21 switch in Figure 2. The path had no Hopper support, so p21 added it, on top of p20. (p20 batched host-cache copies into one transfer per run of slots, my agents' own implementation of an idea AutoclickerI described publicly.)

On my rig, a 74K-token prefill went from 6.36 s with stock to 2.74 s. The judge gave **2.208×**, up from 1.457×, which is more than half of the whole track's gain in one run.

### p24: expert swaps

Each GPU holds 32 of the 256 experts in each layer, and a token's work lands on whichever GPUs hold its experts. Routing traces from a real-weight run showed the busiest GPU doing about 1.5× the average expert work in a typical layer. Eight swaps per layer, fitted on some traces and tested on others, cut that to 1.13×. The organizers had confirmed in the contest Slack that rearranging experts was allowed.

My rig said +3–5%. The judge said **2.222×**, +0.6%. More swaps didn't help: my greedy swap search stayed at 1.13× on held-out traces from 8 swaps per layer up to 128. Splitting a hot expert's tokens across two GPUs might have gone lower, but I didn't try it.

![Figure 6. Expert-swap balance flattens after eight swaps per layer](/assets/images/okc/serving-swaps.svg)

### p24 + one flag: the KV pool

46 of the model's 62 layers use sliding-window attention, and the other 16 need cache for every token of every conversation. SGLang splits the KV memory between the two kinds by a ratio, `--swa-full-tokens-ratio`, that defaults to 0.8. At 32 users, 32 conversations of 75K+ tokens needed about 2.6M tokens by my estimate, more than the 2.03M full-attention share, which would push some of it out to host memory.

Setting the ratio to 0.25 regroups the same memory, and full-attention capacity went from 2.03M to 3.39M tokens. The later-turn p90 at 32 users fell from 1.45 s to 0.54 s. Fewer reloads from host memory is the plausible reason, but I didn't measure reloads on the judge. On my rig (tested on a p25 build) the 32-user load got 5% faster than without the flag, and the other loads moved by under 1%, no more than two runs of the same p24 build differed by. A free check at 32 users confirmed it on the judge; its result came back about 27 hours after I submitted it. The final scored run, submitted at 00:00 UTC on the last day, read **2.315×** about four hours later.

## What the score was made of

The rules said the score was throughput at stock's interactivity, but not how the judge computed it. On Nov 18 the agents reconstructed the formula from the judge's own reports.

For each load, the judge runs my server at 1, 4, 16 and 32 users and records two numbers: tokens per second per user, end to end, and tokens per second per GPU. The per-GPU count includes every prompt token, cached or not, plus the outputs, about 1.04M tokens per conversation. Stock gets the same treatment. Then, for each load, the judge looks up stock's per-user speed on my curve. When that speed falls between two of my loads, it interpolates in log throughput against log per-user speed (a straight line on log-log axes). My throughput at that point divided by stock's is the load's ratio, and the score is the geometric mean of the four ratios. A load that fails a gate drops off my curve, and its ratio is read from the loads around it; for p13 at 16 users that gave 0.999.

![Figure 7. How the judge reads each load's ratio off my throughput curve, from p19's report](/assets/images/okc/serving-frontier.svg)

Rebuilt from the per-load data in all seven reports, the formula gives each judged score within 0.5%. My first version interpolated linearly in throughput; fitted to p19 alone it looked right, but on later runs it was up to 5% high at 1 user, which is why I now check a rebuilt rule against every saved result. Nate Mauer also reconstructed the rule independently, on his day 5, and [his write-up](https://n8mauer.github.io/musespark-serving/) adds a useful way to read it. At his speeds, stock's 16- and 32-user speeds both fell below his slowest load, so both ratios read his 32-user throughput and half his score sat on that one load. The 32-user ratio matches exactly, and the other ratios differ by up to about 1.1%. The reports say `paired_reps: 3`, although the 32-user load ran once, and I only have the means. Pairing may explain the difference, but I can't see the judge's code.

Three consequences shaped the rest of the track. For each load, the ratio is read between the two surviving runs whose speeds bracket stock's, so a gain at 4 users also lifts the 1-user ratio. p19's raw time ratios were 1.25, 1.33, 1.45 and 1.46, and the judged ratios were 1.43, 1.46, 1.48 and 1.46. When stock's speed is below my slowest run, the ratio reads that run directly. That was true at 32 users in every run, and from p21 on at 16 users too, so two of the four ratios used my 32-user throughput. And the first turn sets a ceiling. In my budget model, with prefill held at p21's times, even infinitely fast decode only reaches about 3.1×. That model put p21 itself at 1.78×, below the judged 2.21×, so treat the ceiling as rough. Going further means speeding up the first turn, the 74K-token prompt each conversation starts with.

My two biggest steps were both about the first turn. Over the seven runs, the time to first token at one user went from 9.3 s to 3.8 s.

![Figure 8. Time to first token for the 74K-token first turn at one user, by run](/assets/images/okc/serving-ttft.svg)

Memory shows up in the later turns at 32 users. Their p90 latency fell from 5.25 s to 2.49 s when p15 gave the 13 GB back, and from 1.45 s to 0.54 s with the final flag; in between, it fell with faster kernels too. Those two memory changes raised the 32-user ratio by about 4% and 6%. Most of that load's climb came from p19 (+21%) and p21 (+53%).

## The judge was the bottleneck

In the kernel track, compute was the limit. Here it was the judge's queue. Outside the priority tiers, my scored runs waited between 2 minutes and 11.5 hours for a node, and free checks waited from 9 hours to more than 2 days. A check I filed in the afternoon read back the next morning, sometimes after I had already replaced the patch it was checking. A check I knew was dead (the p12 hang) couldn't be cancelled. It ran 50 hours later and crashed, as expected.

![Figure 10. How long each judge job waited for a node](/assets/images/okc/serving-queue.svg)

I picked up two habits from this. The first was to submit at the reset. The daily scored run reset at 00:00 UTC, and a small script armed the day's choice and sent it at 00:00:30, guarded by the patch's hash so a changed file couldn't go out by accident. The decision lived in a one-line JSON file that the agents could update until a few minutes before the reset, with a fallback if the API refused a flag.

The second was leaning on my own rig. With a day between verdicts, my 8×H200 runs were the only fast feedback, which raised the stakes on them measuring the right thing.

## My rig, against the judge

My rig ranked changes reasonably but sized them badly, in both directions.

![Figure 11. What my rig and models predicted, and what the judge measured](/assets/images/okc/serving-rig-vs-judge.svg)

- p13: the rig said +33% over stock and the judge +7%. The rig's conversations were 4 short turns; the judge's were 13 turns from a 74K-token prompt. Same flags, different workload.
- p21: the rig said +71% over stock and the judge +121%. On the rig, most first turns at 4–32 users were prefix-cache hits, so it underweighted prefill, where sequence parallelism pays.
- p24: the rig said +3–5% and the judge +0.6%. One pass can't size a change of a few percent.
- Prompt lookup (drafting from n-grams of the prompt, which the rules allowed): a CPU replay estimated +8–15%, and the 8-GPU rig measured +0.5%. It was never judged.
- The SWA flag: the rig said +5.6% throughput at 32 users and the judge +6.0%. It was the first change that carried over at about its size, perhaps because it changes memory capacity rather than kernel speed.

After p13, I had the agents move the rig's harness to the judge's shape in steps: 13 turns and 220 output tokens (the judge's average) from n19 (Nov 17), ~74.7K-token first turns from n20b, and fresh conversations per load from n21 (Nov 19). It still sent text to the chat endpoint where the judge sends token IDs, so every later turn re-rendered and re-tokenized the whole conversation. A profile on Nov 18 put the scheduler's share of a later turn at 80–90 ms of the 210–250 ms I measured, and the tokenizing was likely much of the rest.

### What one GPU can and can't tell you

Most experiments didn't need eight GPUs. A "mini engine" on one H200 ran a cut-down slice shaped like one column of Figure 2: one GPU's 16 attention heads and 32 experts at real dimensions, six layers by default, dummy weights, in the judge's image with the judge's graph settings. It was a cheap screen for kernel shapes, graph capture, crashes, and whether a switch changes the outputs, for a few dollars a run. It couldn't see the eight-GPU collectives or the full model's memory.

I was slow to ask what the dummy weights cost me. The mini engine had run on them since the start of November, and I asked why on Nov 15, three days into the track. Timings of fixed-shape work hold, because they don't depend on the values. But the mini engine couldn't measure anything that depends on real tokens: draft acceptance, prompt-lookup hits, real expert routing. Loading one GPU's real weights doesn't fix that, since each layer still lacks the other seven GPUs' share.

The idea I'd use next time is record and replay. One real-weight 8×H200 run records the output tokens and each layer's chosen experts. The judge decodes greedily, so the output depends on the drafter only through small numerical differences. For a drafting rule that looks only at past tokens, like prompt lookup, acceptance can be estimated on a CPU from that trace. A neural drafter like DFlash also reads the big model's hidden states, which a token trace doesn't hold. None of this measures time. The routing trace can be replayed into the one-GPU rig for expert placement. One person in the contest Slack mentioned spending about 300 H200-hours, an anecdote I can't check. Some of the questions those hours answer, like token-based drafting acceptance and expert balance, could be screened from one recorded run. Timing still needs the GPUs.

## Hunting for 3×, and stopping

After p21, I asked the agents for 3×. The serving-lead session's ceiling analysis said the realistic target was about 2.0–2.1× (I passed it) and that decode work alone couldn't reach the scores people were mentioning in Slack. I asked anyway, then said "go hard for 3x", and approved a four-GPU Modal test and one more 8×H200 run.

That bought three things. The first was overlapping the prefill collectives with the matrix multiplies on a side stream. It engaged on all eight GPUs and made prefill about 1% slower in a single pass. My guess was that the collectives queued behind matrix multiplies that already kept the whole GPU busy, but the profiles that would have shown it were lost. The next step would have been copy-engine transfers, which don't use the compute units, and there wasn't time to build and check one. The second was the SWA flag, the one that shipped.

The third was an outside scan. I had Grok look for levers that could reach 3×, and the agents checked each claim against my pinned SGLang source. Most were real mechanisms that didn't fit. More draft tokens didn't, since the drafter was trained for 8 and verifying 16 doubles the work at 32 users. Symmetric-memory collectives reserve 4 GB per GPU by default, which would come out of the KV cache, and checking that wasn't possible before the last slot. More expert swaps were flat past eight, and SGLang only supports an adaptive verify length for a different drafter. None was worth the last day's only scored run without a check, and checks took a day.

On the last day I declined a second 8×H200 run and kept the plan. The last slot went to the change that a judge check had already confirmed.

## The setup, one track later

The organization from the kernel track carried over, with roles adjusted for a track that ran on rented 8-GPU boxes and one verdict a day.

A few things worked better than in the kernel track. The reviewer caught wording as much as bugs. Astra flagged "bit-equal" where the evidence only showed value-equal (twice), a lever I'd already measured on Nov 13, a one-repetition check described as a match, and a mislabelled latency figure in my own prompts.

Before porting the upstream PR, the agents also saved the live rules and the terms and checked them for clauses on third-party code, and I approved each piece with credit kept. And I kept the contest Slack read-only. The organizers' answers there (greedy decoding, prompt lookup and wider verify allowed, expert swaps allowed) went into a notes file as rulings, other people's reports went in as anecdotes, and nothing was posted.

## Wrong turns

1. My rig's workload didn't match the judge's. Same flags, different conversations, and p13's 1.33× became 1.07×. I read the judge's workload report on day 3, and it should have been day 1.
2. Nobody looked at the weight memory. My own logs showed +13 GB from the first validation run. A total-memory gate can't see memory that came out of the cache; only the KV capacity line shows it.
3. I trusted single-pass rig deltas of a few percent. p24's +3–5% was +0.6% on the judge, and prompt lookup's +8–15% replay was +0.5% on the rig. Below about 5%, one pass on my rig told me the sign at best.
4. A profiler never flushed. The n21 first-turn profiles asked for 8 steps, but the 62K-token prompt was only four 16K prefill chunks, so the profiler never stopped and I lost the traces from my biggest run. The harness now stops it explicitly.
5. I planned early and started late. The plan existed from Oct 25, with requesting the gated weights on it. I didn't get around to that until Nov 13, and I was approved within about an hour and a half. No 8-GPU work on real weights could start before that.
6. I questioned the dummy weights late. Expert routing and draft acceptance aren't real on them, and I only asked on Nov 15.

## What I learned

With one verdict a day, the quality of my own measurements decided more than any single idea did. A rig that ranks right but sizes wrong is still useful, as long as I know which of the two I'm asking it.

Memory counts toward the score. The track's cheapest steps were about memory: 13 GB given back, and one flag that regrouped the same memory.

Try the flags first. I found the KV-pool flag two days before the close, and it was worth 4% of my score. Nate Mauer's second scored run was his first run's patch plus the same flag (at 0.15) and the host cache tier switched off, and it took him from 1.05× to 1.20× on his day 2. Launch flags cost nothing to try, and the judge's checks could have measured them in the first week.

Read upstream before writing. My two biggest steps came from code that already existed, an open pull request and a disabled path in SGLang itself.

Plan around the worst queue rather than the last one: arm the submission for the reset, decide the day before, and treat a check as a next-day answer. And I'd put the cap in the launcher again. Every 8×H200 run had an hour cap enforced by the box itself, and the one overspend of the track was a sandbox created before the stop-all command existed.

## In retrospect

What I'd do differently next time:

1. Read the judge's workload on day 1 and reproduce it exactly, token IDs included.
2. Sweep the allowed launch flags with free checks in the first week, before writing code.
3. Request the weights the day I plan to use them, and have a box before the track opens.
4. Record one real-weight run, then replay it for drafting rules and expert placement.
5. Print KV capacity next to every result.
6. Look for disabled paths in the engine before writing new ones.
