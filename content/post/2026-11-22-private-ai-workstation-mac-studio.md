*What a 128 GB Mac can run, how I locked it down, and what happens when the model doesn't fit.*

> **Disclaimer:** An early draft of this post was generated by Claude from my project notes, benchmark results and records. I edited it from there.

In my [last post](/2026/11/20/i-entered-a-gpu-kernel-contest-and-didnt-write-a-kernel/) I mentioned two Qwen models running on my Mac Studio that did the reading for a team of AI agents. This post is about that machine: an Apple M5 Max with 128 GB of unified memory, set up as a private AI workstation.

I wanted two things from it. First, an assistant in the spirit of Muse that I and a couple of people close to me can use from our phones, where nothing we type leaves the house. Second, a replacement for some of my cloud coding tools: local models that do real work, driven by the same agent harnesses I use with hosted models.

I built it the way I ran the kernel contest. Claude did most of the typing; I set the rules, made the calls, and checked the results. The first day, Oct 18, was 31 commits: benchmarks, a chat UI on my tailnet, and a sandbox. The rest has been a month of using it, finding what broke, and pushing on the edges, most recently a 594-billion-parameter model on a 128 GB machine.

## The rules

I gave the project a short list of constraints up front, and most of the design falls out of them.

- **Nothing leaves the machine** except pinned downloads. Every benchmark reads local weights with `HF_HUB_OFFLINE=1`.
- **No Docker and no VMs** except Apple's own [`container`](https://github.com/apple/container) tool, which runs each container as a lightweight VM.
- **Small, self-written tools** in Swift, Python stdlib or Rust, instead of large third-party stacks. Ask before installing anything.
- **Pin everything.** Every runtime and container image is pinned by version and sha256 (or OCI digest), and nothing auto-upgrades. A version change is a proposal with a changelog and a security note.
- **Signed commits** with a key in the Secure Enclave. When I asked for this, I said not to download anything: "it's very simple to write one with Swift". So there's a small Swift tool, se-sign, that signs git commits with a Secure Enclave key and has since grown a gated ssh-agent.
- **Telemetry on every benchmark:** CPU, GPU, ANE and power, through [macmon](https://github.com/vladkens/macmon) without sudo.
- **Verify every launch.** After starting anything, confirm it's actually running: the process, a health check, a log that's growing. This rule came from experience, and it kept paying off.
- **I do the sudo.** System settings, security settings, admin installers and account sign-ins are mine. Claude files them in a Linear issue and waits.

## The stack

![The local AI stack on the Mac Studio](/assets/images/local-ai/architecture.svg)

Here's what runs, top to bottom:

| Component | What it does | Size |
|---|---|---|
| [llama.cpp](https://github.com/ggml-org/llama.cpp) `llama-server` | Serves the chat model (Qwen3.8-Flash-Next, 128K context, speculative decoding) and an agent model (Qwen3-Coder-30B) side by side | prebuilt release, pinned |
| stackd | A small router in front of both: streams responses byte for byte and routes by the request's `"model"` field | 167 lines, Python stdlib |
| [Open WebUI](https://github.com/open-webui/open-webui) | The chat UI, in an Apple container on a host-only network | pinned image digest |
| Socket gateway | The only way in or out of the containers (more below) | 225 lines, Python stdlib |
| Fetch proxy | Lets the chat UI fetch web pages from an allowlist, and nothing else | 173 lines, Python stdlib |
| [Tailscale](https://tailscale.com) `serve` | HTTPS on my tailnet only, with the user's identity in a header | pinned installer |
| expctl | A scheduler that runs GPU experiments only when nobody is chatting | 391 lines, Python stdlib |
| Status page | Jobs, queue, failures and telemetry, for me and the people I share the machine with | 623 lines, Python stdlib |
| Agent containers | One throwaway container per delegated coding task | 113 lines + a 7-line Containerfile |

Everything runs under launchd. The disk is encrypted with FileVault and there's no auto-login, so nothing starts until I log in.

### Locking it down

The interesting part of the security model came from a constraint I didn't plan for. The macOS firewall is set to **block all incoming connections**. That turns out to block TCP between the host and its own container VMs too, in both directions: the container couldn't reach the model server, and publishing a container port on localhost gave "connection reset by peer".

Rather than loosen the firewall, Claude built a gateway over Unix sockets. Apple's `container run --publish-socket` exposes a socket from inside the container on the host. A small host process (`gw_host`) keeps a pool of connections dialed *into* each container. When the container wants out, its sidecar (`gw.py`) claims one of those connections, and the host pipes it to a target that's fixed on the host side: the model, or the fetch proxy. Inbound chat traffic goes the same way in reverse.

The result is that a container can reach exactly two things, the model and the proxy, and it can't name any others. Not the internet, not my LAN, not my tailnet, not other ports on the host.

The fetch proxy is the only path to the web. It allows hosts on a live-reloaded allowlist (arxiv, Wikipedia, GitHub to start), refuses raw IPs, and refuses any host that resolves to a private, loopback, link-local or tailnet address. It then connects to the IP it vetted, so a DNS answer can't change between the check and the connection.

Authentication is Tailscale's identity header. `tailscale serve` adds the visitor's tailnet login to every request; Open WebUI trusts it, the first user became admin, and anyone else lands as pending until I approve them. A password sign-in without the header is refused.

That header is also the main weak spot: any process on the Mac that can reach Open WebUI's local port can forge it. That's why agents only ever run inside containers, which can't reach that port.

A 22-check script (`setup/verify.sh`) proves all of this from scratch:
- the firewall mode, and that every service listens on loopback only;
- the API returns 401 without its key;
- a header-less sign-in is refused;
- from inside a container, the model is reachable while the internet, the LAN, the tailnet and the host bridge are not;
- the proxy allows arxiv and refuses example.com and raw IPs;
- an agent container reaches nothing at all.

## Picking a model

On day one I benchmarked seven models with llama.cpp's `llama-bench`. Every model got the same grid: a 2,048-token prompt and 128 generated tokens, at four context depths, three reps each, all layers on the GPU.

**Generation speed (tokens/s) as the context fills up:**

| Model | Quant | 0 | 8K | 32K | 64K |
|---|---|---|---|---|---|
| Qwen3-Coder-30B-A3B | Q5_K_M | 140 | 104 | 57 | 37 |
| Qwen3.6-35B-A3B | UD-Q5_K_M | 109 | 102 | 88 | 73 |
| gpt-oss-120b | MXFP4 | 109 | 98 | 73 | 56 |
| Gemma 4 26B-A4B | UD-Q4_K_M | 106 | 93 | 77 | 61 |
| Qwen3-Coder-Next | Q4_K_M | 96 | | | 63 |
| **Qwen3.8-Flash-Next** | UD-Q3_K_XL (90 GB) | **47** | **46** | **44** | **43** |
| Gemma 4 31B (dense) | Q4_K_M | 26 | | | 16 |

Qwen3.8-Flash-Next is the slowest of the mixture-of-experts models on an empty context, and by far the flattest: it loses 10% from an empty context to 64K, while the small models lose half or more. Prompt processing shows the same pattern: 1,033 → 852 tokens/s, while Qwen3-Coder-30B drops from 2,986 to 352.

At 120K tokens of context, Qwen3.8 still generates 39 tokens/s; Coder-30B is down to 22. Since a personal assistant spends its time on long documents and long chats, Qwen3.8 became the chat model.

A few more results shaped the setup:

- **Prompt caching is huge.** Asking a second question about the same 31K-token document skips almost all the work: time to first token drops from 13–65 s to 0.06–0.6 s, 41 to 362 times faster. The catch is one slot: if someone else chats in between, the cache is gone.
- **Speculative decoding (MTP)** lets Qwen3.8 draft a few tokens ahead with a small extra module and verify them in one step. It averages 1.48× at 3 draft tokens and 1.59× at 5. Code and JSON reach 1.9× (89 tokens/s); prose gains 1.1–1.3×. It needs the *full* MTP module; the "shared" variant failed to load. On by default.
- **A real 128K chat works.** A 104,742-token document loaded in 137 s with exact recall. Follow-up questions on it came back in under a second from the cache, and memory peaked at 78 GB.
- **KV cache at 8 bits is nearly free** on the Qwen and gpt-oss models (0–4% slower at 64K), but costs Gemma 18–20%.
- **Two models fit at once.** Qwen3.8 and Coder-30B together peak at 108.5 GB with no new swap, for about 1.85× the machine's total throughput. So the chat model and the agent model now run side by side.
- **The Neural Engine sat idle** (0 W) in every llama.cpp run. The GPU ran at 90–98%, and the whole machine drew 120–140 W.

Speed isn't quality, so Qwen3.8 also got a 20-prompt qualitative round with code and shell answers actually executed. It scored 14 pass, 5 partial and 1 fail. The one fail was a shell one-liner using GNU `head` syntax that doesn't work on macOS. The partials were the kind of thing you'd catch in review: 133 words for a 120-word limit, a percentage of the wrong base, stiff Nepali.

It was strong where I care most: it refused a false premise, didn't invent a Nobel winner, and its code passed seven extra edge cases. Two quirks needed fixes. Inside Open WebUI it claimed to have search, calendar and memory tools it didn't have (fixed with a system prompt). It also refused to read back a planted "CONFIDENTIAL" note from my own document until I told it the document was mine.

## Sharing one GPU

A Mac Studio has one GPU, and a benchmark grid wants all of it for hours. I didn't want to schedule experiments around other people's chats, so I asked for the opposite: "When nobody is logged in we should continue with them from our backlog," and when someone opens the chat, pause the experiment and let them chat.

That's expctl. Experiments sit in a JSONL backlog. Someone counts as "present" if Open WebUI saw a request in the last 10 minutes (the gateway touches a file on every inbound request) or the chat model's token counters moved. The scheduler checks every 3 seconds:

- When the machine has been idle for 10 minutes, it stops the chat model, runs the next GPU job, and records the result.
- When someone shows up, it kills the job's whole process group within about 3 seconds, requeues the job, and brings the chat model back.
- Jobs resume from checkpoints where they can.

It grew two more kinds of jobs during the kernel contest:
- **chat jobs** run while idle *with* the chat model up, because the local model is their worker;
- **remote jobs** (GPU runs on Modal) run any time, because they use nothing local.

The status page shows all of it: who's present, what's running with a log tail, recent failures, the queue, and telemetry sparklines. One early bug: refreshing the status page counted as presence, so watching the experiments kept them from running. Health checks now go over the Unix socket instead.

## Bigger than memory

The question I most wanted answered was whether the SSD can stand in for memory. The internal SSD reads at up to ~12 GB/s, which is a lot less than unified memory's bandwidth but a lot more than nothing. A mixture-of-experts model only touches a few experts per token, so maybe the rest can live on disk.

| Experiment | Size | Result |
|---|---|---|
| Qwen3.8 UD-Q4_K_XL, all on GPU | 111 GB, just under Metal's 115 GB limit | 46.0 tokens/s, −3% vs the 90 GB quant |
| Qwen3.8 UD-Q5_K_XL, memory-mapped | 158 GB, more than RAM | 44.3 tokens/s, 975 prompt tokens/s (3 reps) |
| Same, with experts on the CPU (`--n-cpu-moe 8/16/24`) | 158 GB | 31 / 20 / 19 tokens/s: strictly worse |
| DeepSeek-V4-Flash Q2 in DwarfStar, resident | 81 GB | 39–42 tokens/s |
| Same, streaming experts from SSD | 81 GB | 19–28 tokens/s |
| DeepSeek V4.1 Flash Q2 in DwarfStar, SSD streaming | **366 GB, ~3× RAM** | **16–20 tokens/s**, 6.3 GB/s average from the SSD, RAM peak 70 GB |

The first surprise was the 158 GB model. It ran at full speed because the experts it actually uses stay in the page cache, and llama.cpp's memory-mapped loading handles the rest. The first run was only 9 seconds long and the number looked too good, so I had it rerun longer; it held. For this model, the higher-quality quant was effectively free.

The second was [DwarfStar](https://github.com/antirez/ds4), antirez's Metal inference engine with explicit SSD streaming. It ran a 366 GB DeepSeek model on a 128 GB machine at 16–20 tokens/s. That's slow for chat, but it runs, and the machine stayed usable (no new swap). Its first run failed instantly because it looks for its Metal shaders relative to the current directory. The script still exited 0, so the scheduler recorded the failure as done.

### Inkling 2 Small: 594 billion parameters

Then Thinking Machines released Inkling 2 Small. "Small" is relative: 594 billion parameters, 17 billion active per token, 1M context. The smallest quant that comes close to fitting is bartowski's IQ1_S at 127.5 GB, so it became the stress test.

**Getting it onto the disk.** The pinned llama.cpp predates the `inkling2` architecture, so it got a second, newer pin (b12600) next to the old one; the live services didn't change. The first download ran at 1 MB/s, about 32 hours for 128 GB.

It turned out Hugging Face's CDN speed varies wildly *per connection*: 0.8 MB/s and 21 MB/s on the same file at the same moment. The fix was a ranged downloader: 256 MB segments, 24 connections, each segment written at its offset into a preallocated file, then the usual sha256 check. The 128 GB came down in about an hour.

It had one bug. After a restart, a preallocated file looked complete, so the fetcher counted holes as downloaded. The checksum would have caught it, but only at the very end.

**Getting it to run.** It didn't fit. Metal lets the GPU use about 115 GB of the 128, and the weights alone are 118.7 GiB. I had two options:

- **Raise the cap** with `sudo sysctl iogpu.wired_limit_mb=…` so the GPU can pin ~120 GB. That's the fast way, but pinned memory can't be reclaimed, so macOS and everything else would live in the last few GB. The worst case is a frozen machine.
- **Keep some experts on the CPU** (`--n-cpu-moe`): slower, but nothing extra is pinned, so memory pressure slows things down instead of locking up.

I started with the second. Experts for 8 of the 48 layers on the CPU ran at 30 prompt / 15 generated tokens/s, until the 32K-context test ran out of GPU memory. The grid script swallowed the error and reported success; I only caught it by checking the rows.

A verbose load showed why. At 124K context, the GPU needed 100.5 GB of weights, 4.2 GB of KV cache and **25.2 GB of compute buffer**. The KV cache is small because 40 of the 48 layers only look back 1,024 tokens. The compute buffer grows with the batch size.

So: experts for 10 layers on the CPU and batches of 128 tokens. That's 95.4 + 4.2 + 7.1 = 106.7 GB, which fits at 124K. It was also *faster* than the first setting, presumably because the smaller buffer relieves memory pressure more than two more CPU layers cost. llama.cpp's own auto-fit found a working setting too, at half the speed.

| Context | Prompt tokens/s | Generated tokens/s |
|---|---|---|
| 0 | 46.8 | 18.7 |
| 8K | 42.7 | 17.4 |
| 32K | 31.4 | 15.8 |
| 64K | 12.4 | 11.9 |

That's usable for a question, painful for a long document: reading a 64K prompt takes about 90 minutes. With 8 requests at once, total throughput only reaches 21 tokens/s. The 1-bit quant also costs quality, which the qualitative round will show. The remaining benchmarks are running as I write this. *(TODO: fill in v2 and qual results.)*

## Local models as workers

The second goal was to move real work off Claude. The plan was a ladder: Claude starts the project, and as soon as a local model is viable, Claude hands it more and more of the mechanical work through existing agent harnesses (here, [opencode](https://opencode.ai)), and reviews every result. Claude keeps design, debugging, security and review. Two failures and Claude takes the task back.

Some things worked:

- Qwen3-Coder-30B passed 8 of 10 gate tasks on day one and wrote all 35 benchmark configs.
- Qwen3.8 wrote source-reading digests with line citations that checked out, which made it the reader for the kernel contest.
- Over the next month, 94 tasks went to local models: 55 to Qwen3.8 and 39 to Coder-30B.
- This week Qwen3.8 wrote 12 end-to-end API tests for the tool I use to review these drafts.

Some didn't:

- **False "DONE".** The fetch scripts failed twice, the second time with a confident report that every item was fixed. The contest's review ledger has 8 explicit false DONEs: a model claiming success with no file written. So the rule became: never trust a local model's "DONE", only external tests count.
- **Destructive cleanup.** One batch ran `rm -f *.py` and deleted its own validator. Since then, protected files never come back out of the sandbox, and deletions never propagate.
- **Too much input.** Every Qwen3.8 failure in the contest had more than 150 KB of input, and every success with that much input was pure reading. Inputs are now capped at about 60 KB for Qwen3.8 and 30 KB for Coder-30B.

Each delegated task runs in its own container. It gets a private copy of the task folder, and the model is reachable through the gateway and nothing else. Only new or changed files that aren't protected come back.

## Gotchas

<details>
<summary><b>Things that each cost time once</b></summary>

- **Block-all firewall vs container VMs:** host↔VM TCP is dead in both directions. Unix sockets through `--publish-socket` work.
- **A Mac can't open its own `ts.net` name** (TLS fails on the hairpin). Test from another device.
- **Open WebUI's SQLite database is in WAL mode on a shared mount.** Opening it from the host and closing it deleted the `-wal`/`-shm` files, and the UI showed "Backend Required". Query it from inside the container only.
- **`ENABLE_PERSISTENT_CONFIG=False`**, or Open WebUI's database silently overrides your environment variables.
- **An approved user saw an empty model list** until `BYPASS_MODEL_ACCESS_CONTROL=True`.
- **Open WebUI turns every EPERM into "storage not writable".** It was really the sandbox blocking a fetch to arxiv.
- **launchd's default limit of 256 file descriptors** ran out on a single Open WebUI page load through the gateway (dozens of parallel connections, two descriptors each). Raised the limit, fixed a leak on failed connects, and tested with 400 simultaneous connections.
- **Background jobs started from a terminal session die with it.** Use launchd.
- **zsh doesn't word-split `$VAR`.** Use `${=VAR}`. A benchmark rerun silently did nothing because of this.
- **Qwen3.8's chat template** accepts `reasoning_effort` low, medium or xhigh; `none` is an HTTP 500. Send `enable_thinking: false` instead.
- **Exit codes lie.** DwarfStar's failed first run and the Inkling out-of-memory both reported success. Check the rows, not the exit code.
- **SSD benchmarks read the page cache** if the file was just read: my 12 GB/s figure is an upper bound.

</details>

## What I'm open-sourcing

Most of this is small, dependency-free code that isn't specific to my machine, and I plan to publish it once it's cleaned up:

- **The socket gateway** (`gw_host` + `gw.py`): container networking on a Mac with a block-all firewall, with host-fixed targets.
- **The fetch proxy:** an allowlist proxy that refuses private addresses and DNS rebinding.
- **expctl:** an idle-time GPU scheduler with presence detection and preemption.
- **stackd:** a streaming model router for llama.cpp servers.
- **The pinned downloader** (`fetch_ranged` + `fetch_weights`): resumable, multi-connection, sha256-verified Hugging Face downloads.
- **se-sign:** git commit signing and a gated ssh-agent backed by the Secure Enclave, in one Swift file with no dependencies.
- **draft-review:** the std-only Rust server I use to review drafts like this one from my phone, with comments and agent suggestions.
